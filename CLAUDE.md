# Log Monitoring

Support-first observability for on-prem Windows deployments. The goal is that a support engineer can investigate a customer issue **without opening massive raw log files**.

## The plan is the source of truth

The VitePress site under [`site/guide/`](site/guide/) is authoritative. Read it before making implementation decisions — especially [`architecture.md`](site/guide/architecture.md), whose *"Current state vs. what is left"* table is the live status of every component.

## Context you cannot get from this repo

- **The application being monitored is `rndfwcore`, at `D:\GitProjects\rndfwcore`.** It is a large .NET 8 enterprise framework (server / service / engine / web / logic). Its chokepoints are instrumented on its `log-monitoring` branch (not yet merged to `dev`); the pipeline has been verified end-to-end against it.
- `rndfwcore` writes its `SystemTrace_*.log` files from `server/server.logging/sinks/FileSink.cs`.
- The `log-monitoring` branch is checked out in a worktree at `D:\GitProjects\rndfwcore-log-monitoring`; the main checkout stays on `dev`. A fresh worktree needs `BUILD/RUNTIME/dlls/thirdparty/` copied from the main checkout (it is gitignored). There is no repo-wide solution: build the single-project `.sln` files in `BUILD/BuildAll.bat` order (Common, Shared, Resources, Engine, Logic, Client, Init, Admin, Service, Server; the per-section lists are in `BUILD/modulesSolutions.config.yml`). Skipping a section leaves stale DLLs from an older framework version in `bin`, which shows up as CS0012 "defined in an assembly that is not referenced ... Version=8.2.0.0"; with every section built, all projects compile. From an agent shell pass the machine's `.snk` signing flags. Projects reference each other through `Private=False` HintPath DLLs, so NuGet packages added to libraries never reach host bin folders; hosts (server.service, server.console) need their own PackageReferences. An assembly that only sits beside `server.console.exe` is not bindable: it must be in the exe's `deps.json` or under a `dlls\*` folder the startup sweep (`AssemblyHelper.LoadAssemblies`) walks.
- `rndfwcore` uses central package management (`Directory.Packages.props`, transitive pinning on): PackageReferences carry no Version. `Microsoft.Extensions.*` must stay on 8.0, so OpenTelemetry is pinned to 1.9.0 (Process instrumentation 0.5.0-beta.7); 1.10+ pulls 9.0 and restore fails with NU1109.
- `rndfwcore` git traps: `.git/info/attributes` sets `* -text -eol`, so git stores bytes as-is; dev stores LF, so write resolved or generated files with LF. The global `submodule.recurse=true` plus the uninitialized `BUILD/pipeline-shared` submodule breaks `merge --abort`/`reset`; pass `-c submodule.recurse=false`. The `log-monitoring` branch tracks `origin/dev`, so push it explicitly (`git push origin log-monitoring:log-monitoring`).
- The pipeline was verified against **rnds4assets** (SQL Server; connection details in its `BUILD\SetUserVars.bat`, company VPN required). Its tables live in schema `master`, not `dbo`; `LOCALTIME` does not exist despite `ColumnNames.cs`. The named instance uses a dynamic port: resolve it through SQL Browser (UDP 1434) and pin a static port before relying on it. `CHECK_POLICY = ON` silently rejects weak passwords in `CREATE LOGIN`. For read-only checks, `sqlcmd` works from an agent shell with the app's own schema logins (`DB_data` etc. in `BUILD\RUNTIME\secrets.json`, passed through `SQLCMDPASSWORD`); anything that creates logins goes to the user as a `! sqlcmd ...` line. Pick a current session with `SELECT TOP 1 SESSIONID FROM master.CLIENTSESSIONLOG ORDER BY CREATEDDATE DESC`.
- **End-to-end flow test (rnds4assets + s4assets mobile app on MEmu), last run 2026-10-12.** Overlay the worktree's freshly built framework DLLs onto `rnds4assets\BUILD\RUNTIME` (never `dlls\android`/`dlls\_android`; originals for everything are in `BUILD\baseruntime\`), plus `server.console.deps.json` and the OpenTelemetry/Grpc/Google.Protobuf DLLs from `server.console\bin\Debug` beside the exe. ITMS's server also binds port 8001, so only one runs at a time. Reproducible failures: a wrong password (method, "Invalid Credentials"); Direct Transfer to location `A002` scanning an unknown tag (method, `BPTransferValidation`); restarting the server under a logged-in device, then any action (`InValidSessionException`, which derives from `MethodException`; the app's "Object reference not set" text is the client mishandling it). Use unknown tags only: a real tag with a live session moves a real asset. No natural server-side *system* error has been found yet; demonstrating one needs an injected fault.

## Decisions that are easy to accidentally undo

- **`src/SystemTraceParser/` is parked on purpose.** It works and has tests, but it is deliberately unwired. `SystemTrace_*.log` files are a local backup that the pipeline does **not** ingest. Do not wire it up — that decision was made explicitly.
- **Kafka is in Milestone 1**, not deferred. `OTel Collector → Kafka → consumers → Elasticsearch/TimescaleDB` is the target pipeline, so the existing compose stack and `src/Consumers/` are the base to build on, not a prototype to strip.
- **One source per signal.** .NET runtime/process metrics come from OTel `AddRuntimeInstrumentation()`/`AddProcessInstrumentation()`, never Telegraf CLR counters. Host metrics come from Telegraf, never the collector's `hostmetrics` receiver.
- **Enrichment happens in the app.** Safe context (session, operation, user) is attached as OTel attributes at emit time. The read-only SQL Server connection is only an *optional on-demand lookup* at investigation time — it is not a per-event enrichment step, and it is not SQL Server performance monitoring.
- **Redaction happens in the application layer**, before telemetry reaches this pipeline. The pipeline stores what it receives.
- **No backward-compatibility shims until there is a stable version.** Compat was dropped on purpose on 2026-08-04 (volumes wiped, Protobuf fallback and `.keyword` sub-fields removed).
- **`elasticsearch-init` creates `logs-000001`/`traces-000001` only when the alias is absent, with `--fail` on every call.** Don't go back to swallowing the 400: after an ILM rollover, re-creating `-000001` would claim `is_write_index` for a second index and writes would stop. `kafka-init`'s `--if-not-exists` is plain restart idempotency; keep it.
- **Never point anything at an ILM-managed index name.** ILM `shrink` renamed indices and hid all warm data from pattern-based datasources; shrink is removed and Grafana queries the aliases.
- **Consumers write `session_id`, `operation_id`, the user field and the logs' `trace_id` as `""` when absent, never omit them.** Dashboards filter with `field:*$var*`, which matches an empty string but not a missing field; omitting them hid every failed login and session-less record. Count distinct sessions with `AND NOT session_id:""`.
- **The app samples traces AlwaysOn in code (`ServiceStartUp.StartTelemetry`).** Requests arrive under an unrecorded Activity from the hosting layer, so the SDK default (ParentBased) silently drops every request span and only startup spans arrive.
- **Spans carry `start_time_us` (Unix microseconds) next to `@timestamp`.** `@timestamp` keeps only milliseconds and a parent and its children usually share one, so the trace drill-down sorts on `start_time_us` to list callers before callees. Grafana's raw-data mode also re-sorts newest-first regardless of the query's `order`, so the sort lives in a `sortBy` transformation.
- **Failures are recorded through `FrameworkTelemetry.RecordException`** (status message, `error.kind` = `method`|`system`, exception event, stack for system only) and raised once per exception object as an ERROR log record by `OtelLogBridge`. Don't go back to inline `AddEvent("exception")` blocks: the Failures panel depends on `error_kind` and on exactly one log record per failure.

## Known gaps in the current code

- Telegraf must still be **installed on each Windows host** (config + install steps in `deploy/telegraf-windows/`); the collector `hostmetrics` receiver and the containerized Telegraf are already removed.
- `rndfwcore` instrumentation lives on its `log-monitoring` branch and is not merged to `dev` yet (dev was merged into it on 2026-10-12). Both hosts now declare the OpenTelemetry packages, so their `deps.json`/`bin` carry OTel plus Grpc and Google.Protobuf, and `CopyProjectOutput.bat` dispatches them; verified by hand on the rnds4assets runtime on 2026-10-12, not yet through the CI dispatch (`CopyProjectOutput.ps1` in pipeline-shared).
- `rndfwcore`'s classic logging (file/DB sinks) dies silently for the whole process when `LoggingManager.Initialize()` throws, because `server.logging` `Factory.IsInitializing` is never reset (no try/finally). A file sink whose path resolves to an unwritable folder (e.g. `C:\SystemTrace_*.log` from a non-elevated server) is enough. OTel logs no longer depend on it, but `SystemTrace_*.log` and DB log sinks still stop; that framework bug is not fixed.
- Dashboards, alerts, datasources, and the DLQ path were verified against the live local stack on 2026-07-24 (provisioning loads clean, parse failures reach `dlq`, `.NET` metric names confirmed). Two things remain unverifiable locally: the `win_*` host metric names (Telegraf has never run against this stack — confirm on the first real host install) and `sql_danger_flags`/job-span shapes (no such documents emitted yet).
- `rndfwcore` does not emit a `host.name` resource attribute, so its telemetry has no `host_name` field; the dashboards' Lucene filters use `(host_name:$host OR (NOT _exists_:host_name))` to tolerate that. The proper fix is app-side, in the instrumentation on the `log-monitoring` branch. (Lucene gotcha: `a OR NOT b` without the inner parentheses matches nothing.)
- Alert notifications use placeholder defaults; set `ALERT_EMAIL_TO` / `ALERT_WEBHOOK_URL` (consumed via `$__env{}` in `docker/grafana/provisioning/alerting/contact-points.yaml`) per deployment.
- The on-demand enrichment lookup is built as an opt-in Grafana MSSQL datasource plus an application-database stored procedure, disabled by default. It was live-verified against a real SQL Server on 2026-08-03 and the deploy scripts are schema-portable (`<<schema>>` placeholder + preflight check), but it still needs per-customer DBA setup, a rotated `mon_session_lookup` password, and a pinned static SQL port. The procedure requires FW >= 2.2.0.0 columns.
- All three consumers use `AutoOffsetReset.Latest` with manual commits, so a consumer group with no committed offset starts at the end and silently drops whatever is already buffered in Kafka (and a group reaped after `offsets.retention.minutes` loses everything buffered while it was away). That contradicts the no-loss buffer goal; switching to `Earliest` is the first Milestone 2 item, paired with a deliberate starting offset because a fresh group would otherwise replay the whole retention window.
- Consumers parse **OTLP JSON only**. The legacy Protobuf fallback was removed once pre-migration records expired; `src/OtlpProto` still vendors the official protos because the generated C# types are what the JSON parser deserializes into. The `OpenTelemetry.Proto` NuGet package does not exist, and `IF.APM.OpenTelemetry.Proto` is a suspected typosquat: never add it. The `.gitignore`'s blanket `logs/` rule hides any vendored path containing a `logs/` folder, so new vendored trees need negation rules.
- Elasticsearch index mappings and ILM are finalized in the `elasticsearch-init` templates in `docker-compose.yml`. Grafana queries the `logs`/`traces` **aliases**, not `logs-*`/`traces-*` index patterns, so ILM can rename indices freely. Strings map to plain keywords via a `strings_as_keywords` dynamic template — dashboard queries use bare field names, not `.keyword` sub-fields. Mapping changes apply only to newly created indices and there is no reindex path: adopting one means wiping the ES volume. Upgrading an existing deployment *without* wiping leaves aggregation panels erroring (`Fielddata is disabled` on the old `text` fields) for the whole retention window, because the alias spans both generations.
- **OTLP/JSON encodes `trace_id`/`span_id` as hex strings, but Protobuf JSON decodes `bytes` as base64.** Google.Protobuf's `JsonParser` follows the Protobuf rule, so IDs arrive mangled — silently, because hex is valid base64 and the lengths are multiples of 4. `src/OtlpProto/OtlpJsonIds.cs` repairs this; always route trace/span IDs through it rather than calling `Convert.ToHexString` on the raw bytes. Tests that build payloads with `JsonFormatter` will **not** catch a regression here, because that emits base64 — the guard test hand-writes collector-style hex JSON. Pipeline checks must assert on identifier values and lengths, not hit counts.

## Gotchas

- Histogram `le` and summary `quantile` labels must be formatted with the invariant culture; culture-sensitive `ToString` yields `"2,5"` on comma-decimal hosts and silently stops matching dashboards.
- Synthetic OTLP test payloads must use the attribute key `session.id`, not `session_id`; the parser promotes only OTel-convention names to top-level fields.
- `OtlpJsonParserTests` must stay in `LogMonitoring.sln`; without it, solution builds never compile the consumers.
- A file bind-mount inside a read-only directory mount can't create its own mountpoint, so the placeholder files under `docker/grafana/provisioning/` are required. Use `--force-recreate` after adding mounts.
- Grafana's table panel only shows `noValue` for a zero-column result, so the session-lookup procedure returns an explanatory row when a session is not found. `noValue` also fills every NULL cell, so the session-lookup panel maps NULL to `—`; without that, a found session's empty fields (Company, OS user, Logout) showed the "No session row found" text.
- Compose interpolates `$` inside unquoted `.env` values and silently mangles passwords.
- In TimescaleDB (Postgres) panel SQL, write template variables as `'${var:raw}'`. Grafana inserts a custom "All" value unquoted and quotes ordinary values itself, so both `$var='All'` and `'$var'` break. Also wrap `labels->>'x'` in parentheses inside `||` concatenations (they share a precedence), and cast `$__timeFrom()::timestamptz` before doing interval arithmetic on it.
- `raw_metrics` stores OTel counters as **cumulative** values, re-exported every minute. Never `SUM(value)` a counter; sum the per-series increase (see the "DB query errors" panel), treating a drop or a gap of over 5 minutes as a process restart.
- An Elasticsearch terms bucket ordered by a percentiles metric needs the percentile named (`"orderBy": "1[95]"`, not `"1"`). Grafana names ES metric columns `p95.0 <field>`, `Max`, `Count`, `Sum`, so organize renames must use those keys.
- A bar gauge or stat over an ES `date_histogram` gets one row per time bucket (with `auto`, often 1 s buckets, mostly empty). For one number over the whole range, bucket by `terms` on `service_name` instead; Elasticsearch metric queries with no bucket aggregation fail in Grafana.
- `sql_id` is a new GUID per SQL execution; group statements by `sql_fingerprint`. rndfwcore sends it as `rndfw.sql.fingerprint`, hashed before it truncates `db.statement` at 4096 characters; the traces consumer computes the same hash from `db_statement` only for spans without it (older rndfwcore builds), where long SELECTs that differ after the cut share a fingerprint.
- `api.request` spans carry `api_operation` (`BPName.Method`, or the command name such as `Login`); group API latency by it, since the span name is always `api.request`.
