The mental model

Docker Compose turns this YAML document into a set of related containers. It creates shared infrastructure first, starts prerequisites, runs two one-time setup containers, and keeps the remaining services alive.

13container definitions
11long-running services
2one-shot init jobs
3telemetry signal types
Sources.NET apps send OTLP; Telegraf collects host and container metrics.
CollectorOpenTelemetry receives, enriches, batches, and routes metrics, logs, and traces.
KafkaDurable topics buffer each telemetry signal and decouple producers from consumers.
ConsumersTwo .NET workers read metrics and logs. No trace consumer is defined here.
Storage & UITimescaleDB stores metrics; Elasticsearch stores logs; Grafana and Kibana query them.

Control side-path

kafka-ui connects directly to Kafka and ZooKeeper so an operator can inspect brokers, topics, partitions, and messages.

Initialization side-path

kafka-init creates topics. elasticsearch-init attempts to create lifecycle policy, template, and first index.

Scope note: the repository README says Kafka is later-roadmap work and Milestone 1 should be simpler. This Compose file is therefore a full-stack prototype/deployment definition, not necessarily the current milestone’s minimum architecture.

DEPENDENCY SEMANTICS

What happens during docker compose up

  1. Compose creates monitoring-net and the named volumes that do not already exist.
  2. ZooKeeper, TimescaleDB, and Elasticsearch can start in parallel because they have no service dependencies.
  3. Kafka starts after ZooKeeper becomes healthy.
  4. After Kafka becomes healthy, kafka-init, Kafka UI, and the OTel Collector can start. The consumers also need their respective databases healthy.
  5. elasticsearch-init, logs-consumer, Grafana, and Kibana can all start after Elasticsearch health passes. They do not wait for one another.
  6. Telegraf starts after the Collector container starts, not after it becomes healthy.
  7. The two init jobs exit; the eleven service containers are intended to continue running.

Crucial distinction: depends_on: condition: service_healthy gates initial start on a healthcheck. It does not create runtime supervision: if Kafka later becomes unhealthy, Compose does not automatically stop or restart its consumers because of that dependency.

What restart: unless-stopped means

Docker restarts a failed or daemon-interrupted long-running container. After an operator explicitly stops a container, it remains stopped until manually started. The init jobs intentionally omit this policy so a successful exit is not treated as something to restart.

OPERATIONAL READING · NOT JUST YAML

Important findings before treating this as production

  1. The Elasticsearch init command is likely broken. Literal quote-only lines wrap the Bash body. Remove those outer quotes; the YAML | block already supplies one command string.
  2. Consumers do not depend on init-job completion. Use condition: service_completed_successfully on the appropriate init job, or make the consumers robustly retry missing topics/aliases.
  3. TimescaleDB overrides can break the metrics consumer. Build its connection string from the same TIMESCALE_* variables rather than hard-coding defaults.
  4. Security is development-only. Kafka is PLAINTEXT, Elasticsearch has no auth/TLS, several admin/data ports are published, and default passwords are embedded in the file.
  5. Host bindings are broad. Use loopback bindings such as 127.0.0.1:9200:9200 for local-only tools, or place authenticated/TLS reverse proxies and firewall policy in front.
  6. Single replicas mean no high availability. Kafka partitions and Elasticsearch primary shards have no redundant copy. Named volumes protect against container replacement, not disk or host failure.
  7. Floating image tags reduce reproducibility. Pin exact Kafka UI and TimescaleDB versions (ideally immutable digests) before controlled deployment.
  8. The 10k–50k events/second target is only a comment. No CPU/memory limits, disk throughput guarantees, load test, or capacity enforcement exists in this file.
  9. Retention can consume substantial disk. Kafka’s 10 GiB limit is per partition; two 12-partition telemetry topics could each approach roughly 120 GiB before time retention wins, plus other topics and overhead.
  10. Not every defined path is active. There is no trace consumer; alerts and dlq have no visible users here; otel-checkpoint is unused; port 8889’s exporter is configured but not attached to a pipeline.
  11. Some healthchecks test configuration or TCP only. A valid Collector config does not prove Kafka export works; an open ZooKeeper port does not prove higher-level correctness.
  12. Linux host monitoring does not equal native Windows monitoring. The Telegraf mounts and enabled plugins target Linux. Native Windows counters need a Windows agent/config or another collection path.
  13. Fixed names and subnet constrain coexistence. Explicit container_name values can collide with other projects, prevent scaling, and the fixed 172.28.0.0/16 may conflict with local networks/VPNs.
  14. Initialization has “first boot” semantics. PostgreSQL’s mounted init.sql only runs against an empty data directory. Updating the file later does not migrate an existing named volume.

Bottom line: the file is valid Compose and communicates a coherent prototype architecture. Its strongest qualities are clear service separation, persistent state, health-gated startup, pinned core versions, explicit topics, and internal DNS. Production readiness requires fixing initialization ordering/script behavior, aligning credentials, reducing exposure, adding security and backups, and proving capacity.
