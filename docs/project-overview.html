01 The target — what "done" means

The north star is deliberately narrow and human: a support engineer should be able to investigate a real customer issue without opening massive raw SystemTrace_*.log files.

Answer fast

“What failed around this time?” in under 5 minutes.

Search, don’t scroll

By session, operation, BP/DQ, SQL, component, time window.

See slow & risky

Slow API/BP/DQ/SQL and risky data-change SQL surfaced automatically.

Stay local

Data stays on the customer site by default; forwarding is opt-in.

Deploy anywhere

Same app server or a dedicated monitoring box; online or offline install.

Basic alerts

Service down, ingestion stopped, disk full, error spikes, slow ops.

02 Component map

One telemetry source: OpenTelemetry emitted by the app, plus Telegraf on the host for server health. SystemTrace_*.log files keep being written as a local backup but are not ingested — the parser project stays in the repo, unwired.

Enrichment happens in the app

The app holds the support context when an event happens, so it attaches safe context (session_id, operation_id, username, environment) directly as OTel attributes. Sensitive customer/entity details are not stored per-event — they’re resolved on demand at investigation time through the optional read-only SQL Server lookup.

Where the code stands. The three earlier blockers are resolved. rndfwcore is now instrumented on its log-monitoring branch — API, jobs, BP, DQ, SQL spans and metrics, an OTLP log bridge, session/user attributes — and the full pipeline (app → OTel SDK → collector → Kafka → consumers → ES/Timescale) was verified end-to-end against a real deployment (rnds4assets) on 2026-07-22. There are now three consumers — logs and traces into Elasticsearch, metrics into TimescaleDB — so the missing-traces gap is closed. Host-metrics double-collection is gone: the collector hostmetrics receiver and containerized Telegraf are removed, with native Windows Telegraf config under deploy/telegraf-windows/. Honest remaining gaps: the Grafana dashboards and alert rules were authored while the Docker stack was down and still need reconciling against live data (unverified metric names are flagged in panel descriptions); Telegraf still has to be installed as a service on each Windows host with real FWCORE service names; the instrumentation branch must be merged to dev and packaged so the OTel DLLs land in deployed bin folders; and the optional SQL Server session-enrichment lookup is still unbuilt.

05 My rating

Scored as a plan + working codebase, not yet a shipped product. The thinking is unusually mature and the code has now largely caught up to the plan; the remaining gap is live-stack verification and rollout, not core implementation.

Strategy & scope

9/ 10

Picking support triage as the first user and ruthlessly deferring HA and AI/ML is exactly the right call. Non-goals are written down explicitly — rare and valuable.

Architecture fit

8/ 10

A single OpenTelemetry pipeline with app-level enrichment is clean and correlation-friendly. ES-for-search / Timescale-for-metrics is a standard, defensible split. Each component is designed to stand alone.

Documentation

9/ 10

The VitePress site is genuinely good: field model, thresholds, sizing profiles, security posture, and success criteria all specified. A new engineer could onboard from it.

Code ↔ plan alignment

9/ 10

The code now matches the target pipeline end to end: app instrumented, collector → Kafka → three consumers → ES/Timescale verified against a real deployment. Host-metric double-collection is fixed and DLQ core landed. What's left is rollout, not architecture.

Implementation maturity

8/ 10

The value layer is largely built: three consumers, five provisioned support-first Grafana dashboards, 18 file-provisioned alert rules with pinned datasource UIDs, and a Prometheus service for pipeline-health panels. Held back from higher by the still-down live stack (dashboards need reconciling against real data), placeholder alert destinations, and the unbuilt enrichment lookup.

Risk & security posture

8/ 10

Local-first, read-only enrichment, opt-in forwarding. Redaction pushed to the app layer is a defensible scope call — but it means the pipeline trusts upstream masking, which must be verified.

Strengths

  • Correct altitude. The plan shrinks the next step while keeping the north star — the roadmap literally says so.
  • Concrete success criteria & thresholds (API >3s warn / >10s crit; SQL >1s / >5s), so “done” is testable.
  • Deployment realism. Same-server vs dedicated profiles, online vs offline install, disk-sizing formula — this is on-prem reality, not slideware.
  • Instrumentation is live. rndfwcore is instrumented directly on its log-monitoring branch (traces, metrics, a log bridge) and the full pipeline was verified end-to-end against a real deployment; the SystemTrace parser stays parked in the repo as a fallback.

Risks & gaps

  • top risk  Dashboards and alerts aren't verified against live data. They were authored and cross-validated against code/config while the Docker stack was down; unverified metric names are flagged in panel descriptions and need reconciling once the stack is back up.
  • Rollout is unfinished: the instrumentation branch still needs merging to dev and packaging so the OTel DLLs reach deployed bin folders, and Telegraf must be installed as a Windows service on each host with real FWCORE service names.
  • Placeholder alert destinations: email/webhook contact points default to ALERT_EMAIL_TO/ALERT_WEBHOOK_URL env vars — no alert reaches a human until those are set per site.
  • Enrichment lookup still unbuilt: the optional read-only SQL Server session → customer/entity lookup is specified but not implemented.
  • Unvalidated assumptions: real daily log volume and final ES index mappings/shards remain open questions to confirm against production traffic.
  • Redaction trust boundary: if the app doesn’t mask a secret, the pipeline stores it in plaintext by design. Needs a verification step, at least a sampling check.
Bottom line — 8.5 / 10. A well-reasoned plan the code now largely implements: the app is instrumented, the pipeline is verified end-to-end, and the support-triage value layer — dashboards, alerts, DLQ — is built. Instrumentation is no longer the blocker. The biggest remaining levers are live-stack verification of the dashboards and alerts against real data, building the enrichment lookup, and finishing rollout — branch merge, packaging, and Telegraf host installs.
