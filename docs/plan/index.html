Project recap

Build a practical monitoring system around the logs you already have.

The project is for our own on-prem customer deployments, where the application usually runs as a Windows service on one server. The first usable version should help support find errors quickly, identify slow operations, and investigate risky SQL/data changes.

Last updated: 2026-07-07 Primary user: Support team Deployment: Windows on-prem Retention: 14-30 days searchable

Direction

The original plan has a solid backbone, but it needs to be refocused around current reality: very large existing application logs plus direct OpenTelemetry instrumentation.

  • Keep Elasticsearch, TimescaleDB, Grafana, OpenTelemetry, and Kafka in the architecture.
  • Make Milestone 1 support-first, not AI-first or cluster-first.
  • Support same-server and separate monitoring-server deployments.
  • Use Docker Compose as the primary deployment model.

Key adjustment

The first pipeline must ingest both sources:

  • Existing `SystemTrace_*.log` files, because they already contain API, BP, DQ, SQL, session, operation, and timing details.
  • OpenTelemetry from app code, because we can modify the application and add better correlation, traces, metrics, and structured events.

Priority order

Rank Need What the system should answer
1 Find errors fast What failed in this customer/time window, and which session, operation, BP, DQ, SQL, or service component was involved?
2 Find slow operations Which API, business process, data query, SQL statement, or scheduler job is slow?
3 Detect dangerous SQL/data changes Are there high-risk updates/deletes, high row counts, missing WHERE clauses, or unusual table/entity changes?
4 Understand one request/session What happened across the timeline of a `SessionID`, `OperationID`, API call, job, BP, DQ, and SQL execution?
5 Reduce huge log-file pain How do we search, retain, archive, and rotate large logs without manually opening massive files?

Known environment

  • Customer deployments are on-prem.
  • Windows service hosting is the current norm.
  • SQL Server is the app database.
  • Docker is acceptable.
  • Online and offline installation modes are required.

Target hardware

  • 4+ CPU cores.
  • More than 8 GB RAM, with 16 GB+ preferred.
  • About 1 TB disk.
  • Ability to ask customers for more cores/RAM when needed.

Non-negotiables

  • Redact SQL parameters and secrets.
  • Use read-only DB access for enrichment.
  • Keep data local by default.
  • Make central forwarding optional and filtered.
