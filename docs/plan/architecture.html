System shape

Dual-source telemetry pipeline

The system should not choose between existing logs and OpenTelemetry. It should use both: logs give immediate value for current deployments, and OpenTelemetry gives cleaner structured traces and metrics going forward.

Milestone 1 flow

Windows app service API, background jobs, BP/DQ, SQL execution, errors.
OpenTelemetry SDK Traces, metrics, structured logs, correlation fields.
OTel Collector Receives, batches, enriches, routes telemetry.
TimescaleDB Time-series metrics, summaries, alert inputs.
SystemTrace log files Large pipe-delimited logs already produced by the app.
Log parser agent Tails files, parses fields, redacts secrets, enriches sessions.
Elasticsearch Searchable logs, errors, SQL text, timelines, support filters.
Grafana Support dashboards, searches, alert state, notifications.

Kafka is intentionally shown as a later pipeline stage. It remains part of the target architecture, but Milestone 1 can prove parsing, redaction, enrichment, search, dashboards, and alerts first.

SystemTrace parser

The sample log format is pipe-delimited and includes structured values that should be extracted into fields rather than treated as plain text.

  • Timestamp with timezone.
  • Log type such as Trace or Performance.
  • Component/category and event name.
  • Service/module/class/method context.
  • `SessionID`, `ClientRequestTranID`, `OperationID`, and thread ID.
  • Total elapsed and last log elapsed.
  • Message and data payload.
  • SQL ID, transaction ID, execution time, rows affected, result summary, connection string.
  • BP/DQ names and method names.

OpenTelemetry instrumentation

Instrumentation should be added across the app, not only around HTTP calls.

  • API request spans with endpoint, method, status, duration, and user/session context.
  • Windows service job spans with job name, run ID, status, and duration.
  • BP spans with BP name, method, session, operation, and result.
  • DQ spans with query object name, method, and operation type.
  • SQL spans with redacted SQL text, execution time, rows affected, and danger flags.
  • Metrics for request counts, error counts, operation duration, queue/job runs, and ingestion health.

Field model

Field group Examples Purpose
Identity `customer_id`, `site_id`, `environment`, `server_name`, `service_name` Filter dashboards and support searches by deployment.
Correlation `session_id`, `operation_id`, `client_request_tran_id`, `trace_id`, `span_id` Connect logs, traces, API calls, BP/DQ calls, and SQL events.
Application `component`, `event_name`, `bp_name`, `bp_method`, `dq_name`, `dq_method` Find where a failure or slowdown happened in the app stack.
SQL `sql_operation`, `sql_text_redacted`, `tables`, `execution_ms`, `rows_affected`, `danger_flags` Search slow and risky SQL without storing parameter secrets.
Outcome `severity`, `status`, `error_type`, `message`, `duration_ms` Drive triage, dashboards, and alerts.
Architecture principle Each component should be useful alone: the parser should produce validated events, the OTel package should emit good telemetry, the collector should route reliably, and dashboards should still explain what is happening if one data source is temporarily missing.
